# ADR-004: Star schema with separate sample and variant dimensions

**Status:** Accepted

## Context

Genomic variant data has two natural axes: the variant (genomic position, alleles, annotations) and the sample (individual, population, sequencing platform). A variant call connects them — "in sample S, at position P, we observed alleles A/B with read depth D".

The warehouse design has to support queries like "all variants in BRCA1 with allele frequency < 0.01 in non-Finnish Europeans" (variant-driven) and "all loss-of-function variants observed in any sample of Yoruba ancestry" (sample-driven). Both directions must be efficient.

## Decision

Use a **classical star schema** in the Silver layer with one fact table and three dimensions:

- `fact_variant_call` — the central fact, one row per (variant × sample × call)
- `dim_variant` — one row per unique variant
- `dim_sample` — one row per sample
- `dim_population` — one row per population (and continental aggregate)

Both dimensions use **surrogate integer keys** (`variant_key`, `sample_key`, `population_key`) generated by BigQuery. The natural keys (variant chromosome + position + alleles for variants, sample ID for samples) are preserved as separate columns but are not used for joins.

## Alternatives considered

**Single denormalised table**

- One wide table with every variant attribute repeated for every sample × call combination
- Maximum query simplicity — no joins needed
- Wildly wasteful at this data size: gnomAD has ~750M variants × thousands of samples × dozens of attributes per variant
- Updates to variant annotations become a billion-row rewrite

**Snowflake schema** (dimensions normalised into sub-dimensions)

- More normalised — population continent split into `dim_continent`, gene annotations split into `dim_gene`
- Saves storage at the cost of more joins per query
- BigQuery storage is cheap; query cost grows with bytes scanned, which grows with join complexity — snowflake costs us at query time more than it saves us at write time

**Data vault**

- Hubs, links, satellites — designed for environments with high schema churn and many source systems
- Adds modeling complexity that doesn't pay off for two stable, well-known source datasets
- Worth reaching for if/when we ingest from many heterogeneous sources

## Consequences

**Positive**

- Most queries become a single join from `fact_variant_call` to one or two dimensions — readable, fast, BigQuery-optimisable
- Surrogate integer keys join faster than string natural keys; they're also stable across upstream changes (gnomAD occasionally revises variant identifiers — surrogate keys don't move)
- Clear ownership of which attributes live where: anything that describes a variant goes in `dim_variant`, anything that describes a sample goes in `dim_sample`, anything specific to a single observation goes in `fact_variant_call`
- Standard pattern that any data engineer or analyst will recognise on day one

**Negative**

- Schema-on-write discipline — every new attribute needs a decision about which table it belongs in
- Surrogate keys require a join even when the natural key would be obvious; tooling has to make this ergonomic
- Population analytics involve a three-way join (fact + sample + population) which has to be carefully clustered on BigQuery for performance

## Partitioning and clustering

`fact_variant_call` is partitioned by `chromosome` (a low-cardinality field that almost every query filters on) and clustered by `position` (which gives genomic-region queries pinpoint pruning). The dimension tables are small enough to remain unpartitioned and rely on caching.

## Future revisit triggers

This decision is worth re-examining if any of these become true:

- A use case emerges where queries consistently need to join three or more dimensions, and the join cost becomes prohibitive
- The team standardises on a different modeling pattern (Activity Schema, OBT) across the broader data platform
- A column store optimisation makes the denormalised approach competitive on cost (BigQuery doesn't materially change this trade-off today)
